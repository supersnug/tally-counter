Target-to-Codebase Gap Report
Executive Summary
The current implementation provides a functional local counter foundation and partial scripting, sharing, group, and customization infrastructure. It is not yet conformant with the approved PRD or feature plans.
The most serious differences are:
Local Counter scripts and customizations can enter cloud payloads or be overwritten by cloud state.
Persisted or imported scripts can execute automatically and under the wrong language.
Public embeds serialize private source fields and lack a versioned validation boundary.
Account deletion can cascade into group deletion without ownership transfer.
Synchronization, backup, import, Counter Copy, and Trash lifecycle operations lack the required atomic data boundaries.
Group scripts, lifecycle, permissions, normalization, and conflict behavior remain substantially incomplete.
Accessibility, malformed-data recovery, mobile behavior, and browser verification do not meet acceptance requirements.
Critical Findings
1. Local Counter bundle isolation is violated
Current: Cloud payloads filter core localOnly counters but upload the complete scripts and Tally Super objects. Workspace customization may also contain references to Local Counters. Applying cloud state replaces entire script and customization maps, potentially deleting browser-only linked data.
References: src/pages/CountersPage.tsx:323-438, src/pages/CountersPage.tsx:400-412, src/pages/CountersPage.tsx:467-479, src/pages/CountersPage.tsx:740-763.
Target: No part of a Local Counter bundle may enter cloud payloads. Cloud application and every conflict choice must preserve its script, per-counter customization, retained state, and Local-Counter-specific workspace references.
References: docs/product-specification.md:303-320, docs/features/accounts-and-personal-sync.md:39-60, docs/features/counter-bundles-local-trash.md:68-84.
Impact: Local-only script source, customization, and identifying references can leave the browser. Signing in or choosing cloud state can silently strip linked data from Local Counters.
2. Scripts can resume automatically and use the wrong language
Current: Imported and cloud-loaded script records preserve enabled. An effect starts every enabled script during load and hard-codes JavaScript execution regardless of the recorded language.
References: src/pages/CountersPage.tsx:677-693, src/pages/CountersPage.tsx:859-881.
Target: Loaded, imported, copied, or previously running scripts must always start stopped. Source must only be interpreted under its recorded language and require an explicit Run action.
References: docs/product-specification.md:264-267, docs/product-specification.md:341-343, docs/features/automation-runtime.md:62-67, docs/features/automation-runtime.md:105-113.
Impact: A crafted backup or stale cloud record can cause unexpected code execution. TallyScript can be reinterpreted as JavaScript after an interrupted shutdown.

Current: sanitize spreads the original counter object, and encodeCounter serializes that result. Public URLs can therefore contain stable identity, folder, tags, Local Counter status, Trash metadata, and future unknown fields.
References: src/features/counters/model.ts:95-117, src/features/counters/model.ts:167-176, src/features/embed/EmbedComponents.tsx:29-38.

Existing Foundations That Align
The audit also found partial foundations worth preserving:
Browser code uses only public Supabase credentials: src/lib/supabase.js:1-12.
Personal user_data RLS in supabase.sql checks account ownership.
Group tables use membership RLS and mutation RPCs generally check permissions.
Group count operations use row locking and event identities in the latest wrapper.
Sharing PIN hashes are isolated in a private schema.
JavaScript configures the specified CPU, memory, and stack limits.
TallyScript implements the 10,000-iteration uninterrupted-loop limit and resets after sleep.
Explicit permanent deletion from Trash has confirmation and cleans linked script/customization records.
Account deletion preserves browser-resident personal workspace state.
Group-owned records remain separate from personal user_data.
